An AI decision-support tool for street food vendors: forecast tomorrow's
demand, simulate hundreds of possible outcomes, and get a stock recommendation
that stays financially safe — not just "probably right."

## The problem

A street vendor decides how much to prepare every single day with no data, no
forecasting, and no room for error on tight working capital. Overstock and the
excess spoils or gets thrown out — that's cash the vendor can't get back.
Understock and they turn away paying customers on their best days. Today this
decision is pure gut feel.

## The approach

1. **Forecast** — a Random Forest Regressor trained on the vendor's sales
   history predicts tomorrow's demand from weather, weekday/weekend, and
   local-event signals.
2. **Simulate (BazaarTwin)** — rather than trusting one point forecast, the
   engine samples 500 plausible variations of tomorrow's conditions and
   forecast noise, producing a full distribution of possible demand outcomes.
3. **Survival Stock** — for every candidate stock level (60–130 units), the
   engine computes expected profit, expected waste cost, and stockout
   probability across all 500 simulated futures, then recommends the level
   that best matches the vendor's chosen risk personality:
   - **Protect Cash** — minimize wasted stock/spend, even if it means running
     out some days.
   - **Balanced** — maximize expected profit.
   - **Maximize Sales** — minimize the chance of running out, even if it means
     some waste.
4. **Why-explainer** — a plain-language breakdown of how much rain, weekend,
   local events, and the recent sales trend each shift the forecast.
5. **Savings calculator** — compares naive stocking (rounding the raw ML
   forecast) against the recommended Survival Stock, showing the rupees of
   waste avoided and a projected monthly savings figure.
6. **Stock-level comparison table** — the recommended level side by side with
   a few candidates just above/below it, so a vendor can see the trade-off,
   not just trust one number blind.
7. **Bazaar Mesh** — a small stretch feature: if today's numbers show a likely
   surplus or shortage, check a hardcoded set of nearby vendors for one
   selling the same item with the opposite situation, and surface a single
   match (distance, quantity, rupees recovered). No login, messaging, or map —
   intentionally the simplest version of this idea.

## ⚠️ Data disclosure

**All data in this prototype is synthetic**, generated by
[`backend/app/data/generate_data.py`](backend/app/data/generate_data.py) with
realistic-but-fabricated patterns (rain suppresses demand, weekends/events
boost it, mild upward trend, random noise). No real vendor, sales, or
transaction data is used anywhere in this project. This is a hackathon
prototype meant to demonstrate the approach, not a validated production
forecasting system.

## Tech stack

- **Backend:** FastAPI (Python), scikit-learn (RandomForestRegressor), pandas/numpy. No database — CSV + in-memory only.
- **Frontend:** React + Tailwind CSS (Vite).

## Setup & run

### Backend

Requires **Python 3.11+** — `requirements.txt` is frozen to exact versions
(pandas 3.x / numpy 2.5 / scikit-learn 1.9) that only ship wheels for recent
Python. On an older interpreter, relax the pins (`pip install fastapi
uvicorn[standard] pandas numpy scikit-learn joblib pydantic` unpinned) instead.

```bash
cd backend
python -m venv venv
source venv/Scripts/activate      # Windows Git Bash; use venv/bin/activate on macOS/Linux
pip install -r requirements.txt

# (optional — vendor_sales.csv and model.pkl are already committed)
python -m app.data.generate_data
python -m app.models.forecast_model

uvicorn app.main:app --reload --port 8000
```

API docs (Swagger UI) available at `http://127.0.0.1:8000/docs`.

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`. The frontend expects the backend at
`http://127.0.0.1:8000` (override with a `VITE_API_BASE` env var if needed).

## API endpoints

| Method | Path         | Description                                                        |
|--------|--------------|----------------------------------------------------------------------|
| GET    | `/dashboard` | Today's vendor stats (prepared, sold, unsold, revenue, waste, profit) |
| GET    | `/forecast`  | Raw ML demand prediction for tomorrow given weather/event params     |
| POST   | `/simulate`  | Full BazaarTwin engine: Survival Stock + distribution + why + savings |
| POST   | `/mesh/match` | Bazaar Mesh: matches today's surplus/shortage against hardcoded nearby vendors |

## What's implemented vs. future scope

**Implemented in this prototype:**
- Synthetic data generation, Random Forest forecasting (trained on true
  demand, not stockout-censored sales), Monte Carlo simulation, Survival
  Stock optimizer with 3 risk personalities (percentile-of-demand based, so
  all three visibly respond to changing conditions), why-explainer, savings
  calculator, and a stock-level comparison table.
- **Bazaar Mesh** — a deliberately minimal surplus/shortage matcher against a
  hardcoded set of 5 nearby vendors (see Priority 3 in
  [PROGRESS.md](PROGRESS.md) for exactly how simple this was kept: no login,
  messaging, or map).
- A landing page framing the problem in human terms, and a full
  Dashboard + Simulate flow.

**Explicitly future scope (not built now — out of scope for this hackathon submission):**
- Voice input / speech-to-text for vendors who prefer talking over typing.
- OCR / bill scanning to auto-log daily sales instead of manual entry.
- **Bazaar Intelligence / collective learning** — Bazaar Mesh here is
  intentionally a single hardcoded match against 5 fixed vendors. A real
  version — pooling live, anonymized patterns across many vendors to improve
  forecasts and matching faster than any single vendor's own history could —
  remains future scope.
- Government scheme integration (e.g. PM SVANidhi eligibility/credit access).
- User authentication, payments, or persistent multi-vendor accounts.

## Deployment

### Primary path: one Vercel project, both services (recommended)

Vercel's multi-service ("Services") project type can host the frontend and
the FastAPI backend together under one domain, with `/api/*` routed to the
backend and everything else to the frontend — no separate backend host
needed. The root-level [`vercel.json`](vercel.json) already declares this:

```json
{
  "services": {
    "frontend": { "root": "frontend", "framework": "vite" },
    "backend": { "root": "backend" }
  },
  "rewrites": [
    { "source": "/api(/.*)?", "destination": { "type": "service", "service": "backend" } },
    { "source": "/(.*)", "destination": { "type": "service", "service": "frontend" } }
  ]
}
```

To deploy:
1. Push this repo to GitHub (already done for this project —
   `github.com/akshitsharma24-ux/BazzarSathi`).
2. In Vercel, **New Project → Import** the repo. It should auto-detect both
   services (frontend as Vite, backend as FastAPI) from `vercel.json` and the
   directory contents.
3. **Before deploying**, add an environment variable:
   `VITE_API_BASE` = `/api` — this makes the frontend call same-origin
   `/api/...` paths instead of `localhost`, which is required for the
   rewrite rule above to route requests to the backend. (See
   `frontend/.env.example`.)
4. Deploy. Note the resulting single URL (e.g. `https://bazzar-sathi.vercel.app`).
5. **Verify the backend actually answers under `/api`** — hit
   `https://<your-url>/api/dashboard` directly. The backend
   (`backend/app/main.py`) registers every route at both the bare path
   (`/dashboard`) and under an `/api` prefix (`/api/dashboard`) specifically
   because it wasn't possible to confirm ahead of time whether Vercel's
   service-rewrite forwards the full incoming path or strips the matched
   prefix before proxying — this dual registration means it works either way,
   but it's still worth a direct check once live.
6. Update this README's "Live demo" link at the top with the real URL.

CORS is a non-issue here since frontend and backend are served from the same
origin — the `ALLOWED_ORIGINS` env var only matters for the fallback path
below.

### Fallback path: separate Render backend + Vercel frontend

If the single-project Vercel deploy runs into a limit (e.g. the Python
service's dependency size), fall back to two separate deployments:

**1. Backend on Render** (free tier):
- New → Blueprint → connect the repo. Render will detect `render.yaml` at
  the repo root and configure everything (root dir `backend`, build/start
  commands, Python 3.12.7) automatically.
- Alternatively, configure a Web Service manually: root directory `backend`,
  build command `pip install -r requirements.txt`, start command
  `uvicorn app.main:app --host 0.0.0.0 --port $PORT`.
- Once live, note the URL (e.g. `https://bazaarsaathi-api.onrender.com`).

**2. Frontend on Vercel** (as its own single-service project this time):
- Import the repo, set **root directory to `frontend`** (Vercel auto-detects
  the Vite framework preset via `frontend/vercel.json`).
- Add an environment variable `VITE_API_BASE` = the Render URL from step 1
  (no trailing slash) instead of `/api`.
- Deploy. Note the resulting URL (e.g. `https://bazaarsaathi.vercel.app`).

**3. Lock down CORS** (optional but recommended): back in Render, set the
backend's `ALLOWED_ORIGINS` env var to the exact Vercel URL from step 2
(comma-separate if there's more than one, e.g. a preview + prod URL) instead
of the default `*`, then redeploy.

**Railway / Netlify alternative:** `backend/Procfile` + `backend/runtime.txt`
work for Railway's Python buildpack the same way; Netlify auto-detects the
Vite build in `frontend/` (build command `npm run build`, publish directory
`dist`) if you'd rather use that over Vercel.
